<h1 align="center">Hermes Crew</h1>

<p align="center"><strong>Slack-style channels where a crew of persistent Hermes agents work together — with a human in the loop.</strong></p>

> [!WARNING]
> **Work in progress.** Hermes Crew is under active development: expect rough
> edges, breaking changes, and database migrations between updates. Feedback
> and issues are very welcome.

Hermes Crew is a plugin for [Hermes Agent](https://nousresearch.com) that turns your local Hermes profiles into a crew: named agents with their own models, SOULs, skills, and projects, collaborating in channels and threads on your machine. Hermes remains authoritative for every profile's configuration, credentials, memory, and sessions — Crew adds the shared workspace on top.

- **Home** — an operational center: crew status, live agent turns (with Stop), workspace cards, recent activity.
- **Channels** — the main workspaces. Mention agents, scope messages to Hermes projects, read Markdown-rendered replies, branch into threads.
- **Agent Lab** — build and tune agents: identity, avatars (uploaded, palette, or generated by Hermes image generation — pick the image model and optionally your own prompt), a mythological name generator, SOUL, model and behavior with catalog-backed provider/model dropdowns, skills, workspace — all backed by real Hermes profiles.
- **Session console** — jump from any agent turn into the underlying Hermes session and work with the agent hands-on, without leaving the workspace.

Compatibility floor: **Hermes Agent 0.20.0**. Pinned Desktop Plugin SDK baseline: package **0.17.0** at upstream commit `ee472a7fdbbc55924f91ab122dbaa29bd07668b0`. Both supported hosts ship from one codebase: the native Hermes Desktop app and the Hermes web dashboard.

## Quickstart

```bash
git clone <this-repo> hermes-crew && cd hermes-crew
npm install && npm run build
python scripts/install.py     # installs into $HERMES_HOME (default ~/.hermes)
```

Restart Hermes (Desktop app or `hermes dashboard`), enable the **Hermes Crew**
plugin, and open **Crew** from the sidebar. First run walks you through picking
a default responder and creates **#general**; mention an agent to put it to
work, or open **Agent Lab** to name your crew, generate avatars, and pick
models.

## Install

Prerequisites: Node 22.22+, Python 3.11+, Hermes Agent 0.20.0.

```bash
npm install
npm run build
npm run verify:dist
python scripts/install.py
```

`HERMES_HOME` selects the owner profile (default `~/.hermes`). The installer copies:

| Artifact | Destination | Purpose |
| --- | --- | --- |
| `dist/desktop-plugins/hermes-crew/plugin.js` | `$HERMES_HOME/desktop-plugins/hermes-crew/` | Hermes Desktop plugin (self-contained ESM bundle with inlined scoped styles) |
| `dist/plugins/hermes-crew/` | `$HERMES_HOME/plugins/hermes-crew/` | Python backend + web dashboard bundle |
| `dist/skills/hermes-crew/` | `$HERMES_HOME/skills/hermes-crew/` | The `crew-collaboration` agent skill |

Restart or reload Hermes, enable **Hermes Crew**, then open **Crew** in the sidebar. First run creates `#general` with your profiles as members and one default responder.

Upgrades are idempotent: rebuild and rerun the installer; `crew/crew.db` is preserved and schema migrations run automatically.

```bash
# Remove installed code, preserve Crew data
python scripts/install.py --uninstall

# Remove installed code and Crew data
python scripts/install.py --uninstall --purge-data
```

## Using Crew

### Talking to agents

Messages route deterministically — no hidden magic:

- The channel's **default responder** answers untagged messages.
- `@name` mentions (autocomplete with avatars, anywhere in the draft) route to those members; `@all` notifies everyone.
- Members respond per their **activation policy**: `always`, `mentioned`, `observer`, or `disabled`.
- An optional per-channel **classifier** (off by default) can suggest recipients for ambiguous messages.

The composer supports `/` commands: `/all`, `/inherit` `/global` `/project` (message scope), `/profile` `/search` (navigation), `/clear`.

### Threads and reply placement

Agent answers land where the question was asked: channel-level questions get channel-level answers, thread questions stay threaded. Agents can override this per response (`placement` in the intent envelope): a long work log can stream into a thread while the final result posts to the channel. Humans choose the same way — the channel composer posts to the channel, the thread pane's composer stays in the thread.

### Projects and scope

A channel can default to a Hermes project; a single message can attach one without changing the channel; threads inherit the message's project with isolated per-profile session bindings. Crew scoping narrows routing only — actual filesystem access and approval enforcement remain with Hermes execution controls.

### Agent-to-agent collaboration

Every agent response ends with a hidden intent envelope (`inform`, `result`, `question`, `handoff`, `review_request`, `blocked`, `approval_request`, …) that drives routing. Automated chains are bounded: depth limits, pair-repeat limits, and automated-turn budgets are enforced along the causal chain of turns, and any human message resets the budget. The bundled **crew-collaboration** skill teaches agents the full contract.

### Hands-on sessions

Every agent turn records its Hermes session. **Open session** (on activity
entries, their ⋯ menus, and agent messages' ⋯ Activity section) opens the
native session view in-app on both hosts: the web dashboard resumes it in its
chat, Hermes Desktop routes straight to the session. The embedded **Crew
console** (⋯ → "Open in Crew console") stays available for working without
leaving the workspace: full transcript with crew context folded, live
streaming continuation over the gateway, and Stop support.

## The Steward (experimental)

Agent lifecycles sometimes stall for mundane reasons: a model forgets its
routing envelope, a recipient was concurrency-blocked at the moment of
routing, or a worker died mid-turn. The **Steward** is a hidden automation
agent — off by default — that unblocks those paths on a schedule. It is
rule-based (no model calls, effectively free): each sweep re-plans messages
whose named recipients never got a turn and retries orphaned interrupted
turns, with every action still passing the normal depth/budget/pair caps.

Activate and tune it through the plugin API:

```bash
# enable, sweeping every 5 minutes for anything stalled over 5 minutes
curl -X PUT $HERMES/api/plugins/hermes-crew/steward \
  -H 'Content-Type: application/json' \
  -d '{"enabled": true, "intervalMinutes": 5, "stallMinutes": 5}'

# or run one sweep right now (works even while disabled)
curl -X POST $HERMES/api/plugins/hermes-crew/steward/sweep
```

Sweeps piggyback on worker claim polls, so the Steward is active whenever any
Crew surface is open. Settings live in **Agent Lab → Automation → Steward**:
enable/disable, sweep cadence, stall threshold, a manual "Run sweep now", and
an optional **judgment model**. With a (cheap) model picked from the catalog,
ambiguous stalls — nothing named, nothing running, conversation unfinished —
get a single bounded model call per message that decides whom to wake ("this
agent promised a delegation that never happened"); its verdict passes through
the same routing budgets as everything else. Without a model, the Steward
stays purely rule-based and free.

## Schedules (Hermes cron)

**Agent Lab → Automation → Schedules** creates recurring channel messages
backed by Hermes' own cron: each schedule is a real host cron job (it also
appears on Hermes' Cron page) of the cheapest kind — a `no_agent` script job
whose firing posts one message through normal Crew routing. The trigger costs
no model tokens; mention agents in the message and every firing kicks off a
relay exactly like a human kickoff. Cadence accepts the host's formats: cron
expressions (`0 9 * * 1-5`), intervals (`every 30m`), or one-shots (`2h`).
Pause/resume/run-now/delete from the same pane. Firing requires the Hermes
Desktop app or a running gateway (they host the cron ticker).

## Sessions and projects

Every agent turn runs a real Hermes session **under that agent's own
profile**, scoped to the resolved project of the triggering message (message
scope → thread scope → channel default). That is why crew sessions appear in
Hermes' session list grouped under different projects: a globally-scoped
channel produces sessions under each profile's default project grouping,
while a message or channel scoped to a Hermes project runs its sessions with
that project's working directory — which is the point: scope a message to a
project and the agent works inside it.

## Data, recovery, and upgrades

Coordination data lives at `$HERMES_HOME/crew/crew.db` (SQLite, WAL). Back up `crew.db` with its `-wal`/`-shm` siblings while Hermes is stopped, or use SQLite backup tooling. Agent sessions and profile state remain in Hermes. Runtime errors appear in Hermes logs; Crew's durable activity journal survives reloads.
